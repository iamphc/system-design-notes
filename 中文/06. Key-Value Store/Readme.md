# 第 6 章：设计键值存储

## 引言
**键值存储（key-value store）**是一种非关系型数据库，数据以键值对的形式存储。每个键都是唯一的，值通过这些键来访问。本章详细介绍如何设计一个可扩展、高可用的分布式键值存储，支持如下操作：
- `put(key, value)`，用于插入数据。
- `get(key)`，用于检索数据。

### 设计特点
- 键值对较小（<10 KB）。
- 支持大数据量，具备高可用性与可扩展性。
- 自动扩展，一致性可调。
- 低延迟。

---

## 单服务器键值存储
### 实现
- 使用**哈希表（hash table）**在内存中存储键值对。
- 优化手段：
  - 数据压缩（compression）。
  - 把访问较少的数据存到磁盘上。

### 局限
单台服务器的内存有限，因此要实现可扩展性就需要采用**分布式方案**。

---

## 分布式键值存储
**分布式键值存储**把数据分区到多台服务器上，并且必须在 **CAP 定理**所列出的取舍之间做出权衡。

### CAP 定理
1. **一致性（Consistency）：** 所有客户端在同一时刻看到相同的数据。
2. **可用性（Availability）：** 即使部分节点宕机，系统仍能响应每一个请求。
3. **分区容错（Partition Tolerance）：** 即使发生网络分区，系统仍能继续运行。

**取舍：** 根据 CAP 定理，三项保证中最多只能同时满足两项。

<p align="center">
  <img src="../../06.%20Key-Value%20Store/images/cap.png" alt="CAP" width="400">
</p>

#### 系统类型：
- **CP 系统：** 保证一致性与分区容错，牺牲可用性（例如银行系统）。
- **AP 系统：** 保证可用性与分区容错，牺牲一致性（例如最终一致性）。
- **CA 系统：** 保证一致性与可用性，牺牲分区容错。

    **由于网络故障不可避免，分布式系统必须能够容忍网络分区。因此，CA 系统在真实应用中不可能存在。**

    在分布式系统中，分区不可避免。当分区发生时，我们必须在一致性与可用性之间做出选择。例如，如果节点 n3 宕机，
    写入节点 n1 或 n2 的任何数据都无法传播到 n3。反过来，如果数据写入了 n3 但尚未传播到 n1 和 n2，节点 n1 和 n2 就会持有陈旧数据。

    <p align="center">
    <img src="../../06.%20Key-Value%20Store/images/server-down.png"  alt="服务器宕机" width="400">
    </p>
    
- 如果选择 CP 系统，我们必须阻塞所有发往 n1 和 n2 的写操作，以避免数据不一致。
- 如果选择 AP 系统，系统继续接受读请求，即使它可能返回陈旧数据。
  对于写操作，n1 和 n2 继续接受写入，当网络分区恢复后，数据会同步到 n3。

## 系统组件
### 1. 数据分区
- **技术：** 使用一致性哈希把数据均匀分布到多台服务器上。
- **优点：**
  - 服务器增减时自动扩展。
  - 通过虚拟节点实现异构性。一台服务器的虚拟节点数量与该服务器的容量成正比。

### 2. 数据复制
- 为高可用性，把数据复制到 `N` 台服务器上。
- 这 N 台服务器是这样选出的：从数据所在服务器位置开始沿环顺时针走，选取环上最靠前的 N 台服务器来存放数据副本。在引入虚拟节点的情况下，应把副本放在不同的数据中心，以提高可靠性。

    <p align="center">
    <img src="../../06.%20Key-Value%20Store/images/data-replication.png" alt="数据复制" width="300">
    </p>

### 3. 一致性
由于数据在多个节点上都有副本，必须在各副本之间保持同步。
- **法定人数共识（Quorum Consensus）：**
  - `N`：副本总数。
  - `W`：写法定人数（write quorum）大小。一次写操作要被视为成功，必须得到 W 个副本的确认。
  - `R`：读法定人数（read quorum）大小。一次读操作要被视为成功，必须至少等待 R 个副本的响应。
  - **规则：** `W + R > N` 可保证强一致性。
  - W、R、N 的配置是延迟与一致性之间的典型权衡。

    <p align="center">
    <img src="../../06.%20Key-Value%20Store/images/quorum-consensus.png"   alt="法定人数共识" width="400">
    </p>
    
    - 如果 R = 1 且 W = N，系统针对快速读做了优化。
    - 如果 W = 1 且 R = N，系统针对快速写做了优化。
    - 如果 W + R > N，强一致性得到保证（通常 N = 3，W = R = 2）。
    - 如果 W + R <= N，无法保证强一致性。

- **一致性模型**：
  - **强一致性（Strong Consistency）：** 读操作返回的值对应于最近一次更新写入的数据项结果。
  - **弱一致性（Weak Consistency）：** 随后的读操作可能看不到最新写入的值。
  - **最终一致性（Eventual Consistency）：** 只要时间足够长，所有更新都会被传播出去，所有副本最终达成一致。


### 4. 不一致的解决
复制带来了高可用性，但也导致副本之间出现不一致。版本化与向量锁用于解决不一致问题。
- **版本化（Versioning）：** 
    - 使用**矢量时钟（vector clock）**跟踪数据版本并解决冲突。
    - 版本化意味着把每一次数据修改都视为数据的一个新的不可变版本。
        <div>
        <img src="../../06.%20Key-Value%20Store/images/consistent-server.png"   alt="一致哈希" width="400">
        <img src="../../06.%20Key-Value%20Store/images/inconsistent-server.png"   alt="不一致的服务器" height="230">
        </div>
    
    - 服务器 1 修改了名称，服务器 2 也修改了名称。这两次修改是同时发生的。此时我们就有了相互冲突的值，称为版本 v1 和 v2。


- **矢量时钟（Vector Clock）**
    1. **设定：** 矢量时钟是与一个数据项关联的 [服务器, 版本] 对。它可用于判断
        某个版本是先于、后于还是与其他版本相冲突。
        - 假设一个矢量时钟表示为 D([S1, v1], [S2, v2], …, [Sn, vn])，如果数据项 D 被写入服务器
        Si，系统必须执行以下任务之一。
        - 其中：`D` 是数据项。`Si` 是服务器标识符。`vi` 是数据在服务器 `Si` 上的版本计数。

    2. **更新矢量时钟：** 当某个数据项在某台服务器上被修改时：
        - 如果该服务器已在矢量时钟中，则其版本计数加一。
        - 否则，向矢量时钟中添加一个新条目。

    3. **冲突检测：**
        - **无冲突：** 如果版本 X 中的所有计数都小于或等于版本 Y 中的对应计数，则 X 是 Y 的祖先。
        - **存在冲突：** 如果 Y 中至少有一个计数小于 X 中的对应计数，则这两个版本互为兄弟（sibling）。

    4. **冲突解决：** 当检测到冲突（兄弟版本）时，系统依靠应用特定的逻辑或客户端介入来调和数据。

        <p align="center">
        <img src="../../06.%20Key-Value%20Store/images/vector-clock.png"  alt="矢量时钟" width="500">
        </p>

- **挑战：**
  - 增加了客户端的复杂度。
  - 随着更新增多，矢量时钟的体积可能膨胀，需要采用裁剪策略来限制其大小。


### 5. 故障处理

#### a. 故障检测
仅仅因为另一台服务器说某台服务器宕机了，就认定它宕机，这是不够的。通常，需要至少两个独立的信息来源才能把一台服务器标记为宕机。
- **Gossip 协议：**
    <div style="margin-left:3rem">
        <img src="../../06.%20Key-Value%20Store/images/gossip-protocol.png"  alt="Gossip 协议" width="600">
    </div>

    - 每个节点维护成员 ID 和心跳计数。
    - 每个节点周期性地递增自己的心跳计数。
    - 每个节点周期性地向一组随机节点发送心跳。
    - 如果某个成员的心跳在超过预定义的周期内没有增加，就认为该成员已离线。



#### b. 临时故障
- **宽松法定人数（Sloppy Quorum）：** 临时使用健康节点维持运行。
        <p align="center">
        <img src="../../06.%20Key-Value%20Store/images/sloppy-quorum.png"   alt="宽松法定人数" width="400">
        </p>

    - 检测到故障后，系统需要部署某些机制来确保可用性。
    - 系统不强制要求法定人数，而是在哈希环上为写操作选择最先遇到的 W 台健康服务器，为读操作选择最先遇到的 R 台健康服务器。
    - 离线服务器被忽略。如果某台服务器不可用，会由另一台服务器临时处理请求。


- **暧昧指路（Hinted Handoff）：** 离线服务器恢复后追平变更。
    - 当宕机的服务器重新上线时，变更会被推送回去，以达成数据一致性。

#### c. 永久故障
- 使用 **Merkle 树（Merkle Tree）**在副本之间高效同步。
    **Merkle 树**（或称哈希树）是一种数据结构，用于在永久故障期间高效检测并解决副本之间的不一致。

- 工作原理
    1. **结构：**
        - **叶节点（Leaf Nodes）**存储各个数据块（block）的哈希。
        - **非叶节点（Non-Leaf Nodes）**存储其子节点的哈希。
        - **根哈希（root hash）**代表树中所有数据的综合状态。

    2. **构建 Merkle 树：**
        - **第 1 步：** 把键空间划分到各个存储桶（bucket）中。
            
            <img src="../../06.%20Key-Value%20Store/images/key-bucket.png"   alt="键存储桶" width="500">

        - **第 2 步：** 使用均匀哈希对存储桶中的每个键求哈希。

            <img src="../../06.%20Key-Value%20Store/images/hash-key-bucket.png"   alt="键存储桶哈希" width="500">

        - **第 3 步：** 为每个存储桶生成一个单一哈希。
        
            <img src="../../06.%20Key-Value%20Store/images/hash-bucket.png"   alt="存储桶哈希" width="500">

        - **第 4 步：** 把各存储桶的哈希组合起来，计算更高层的哈希，最终得到根哈希。

            <img src="../../06.%20Key-Value%20Store/images/merkel-tree.png"   alt="Merkle 树" width="500">



    3. **同步：**
        - 要同步两个副本：
            - 比较它们的根哈希。
            - 如果根哈希一致，说明两个副本是一致的。
            - 如果根哈希不一致，则递归比较子哈希，找出不一致的存储桶。
        - 只同步不一致的数据。

- 优点
    - **高效：** 只同步不一致的数据，减少数据传输。
    - **可扩展：** 对大型数据集同样有效，同步开销极小。
    - **可靠：** 确保各副本之间的数据一致性。


### 6. 处理数据中心故障
- 把数据复制到多个数据中心，以确保故障期间仍可用。

## 写路径与读路径
### 1. 写路径（基于 Cassandra 架构）

- 把写入持久化到**提交日志（commit log）**中。
- 把数据保存到**内存缓存**中。
- 当缓存写满时，把数据刷写到磁盘上的 **SSTable**（有序字符串表，Sorted String Table）。

   


### 2. 读路径
<div style="margin-left:3rem">

- 如果没有命中，则使用**布隆过滤器（Bloom Filter）**在 SSTable 中定位数据。
- 取出并返回数据。

## 最终架构

<p align="center">
<img src="../../06.%20Key-Value%20Store/images/final-architecture.png"   alt="最终架构" width="500">
</p>


- 客户端通过简单的 API 与键值存储通信：get(key) 和 put(key, value)。
- 协调节点（coordinator）是一个在客户端与键值存储之间充当代理的节点。
- 节点使用一致性哈希分布在一个环上。
- 系统完全去中心化，因此节点的添加与移动可以自动完成。
- 数据在多个节点上都有副本。
- 由于每个节点承担相同的职责集合，因此不存在单点故障。
