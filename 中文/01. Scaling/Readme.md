# 第 1 章：从零扩展到百万级用户

## 引言
将系统扩展到支持百万级用户是一段复杂、迭代的旅程，需要不断打磨与优化。本章介绍如何从单服务器架构起步，逐步扩展架构，以承载百万级用户。

---

## 第 1 节：单服务器架构
起初，所有组件（Web 应用、数据库、缓存）都运行在同一台服务器上。

<div style="margin-left:3rem">
   <img src="../../01.%20Scaling/images/single-server.png" width="400" />
</div>

### 请求流程
1. 用户通过域名（例如 `api.mysite.com`）访问应用，域名经域名系统（DNS）解析为 IP 地址。
2. Web 服务器的 IP 地址返回给浏览器或移动应用。
3. HTTP 请求被发送到 Web 服务器，服务器返回 HTML 或 JSON 响应。

### 流量来源
1. **Web 应用：** 使用服务端语言（如 Python、Java）实现业务逻辑，使用客户端语言（如 JavaScript、HTML）负责页面呈现。
2. **移动应用：** 使用 HTTP 与 Web 服务器通信，以 JSON 进行轻量级数据交换。

---

## 第 2 节：数据库分离
随着用户规模增长，数据库被迁移到专用服务器上，以便 Web 层与数据库层可以独立扩展。

<div style="margin-left:3rem">
   <img src="../../01.%20Scaling/images/database.png" width="400" />
</div>

### 数据库选型

1. **关系型数据库（SQL）：** 以表格形式存储结构化数据。示例：MySQL、PostgreSQL。
2. **非关系型数据库（NoSQL）：** 适合非结构化数据或低延迟需求。类别包括：
   - 键值存储
   - 图数据库
   - 列式存储
   - 文档存储

- 非关系型数据库可能是正确的选择，当：
   - 应用要求极低延迟。
   - 数据是非结构化的，或者不存在关系型数据。
   - 只需要对数据进行序列化和反序列化（JSON、XML、YAML 等）。
   - 需要存储海量数据。

---

## 第 3 节：垂直扩展与水平扩展
### 垂直扩展
- 为现有服务器增加更多资源（CPU、内存）。
- 受硬件限制，且缺乏冗余。

### 水平扩展
- 向服务器池中加入更多服务器，更适合大规模系统。
- 使用负载均衡器（load balancer）在服务器之间处理请求路由。
---

## 第 4 节：负载均衡器

<div style="margin-left:3rem">
   <img src="../../01.%20Scaling/images/load-balancer.png" width="400" />
</div>

**负载均衡器**将流量分发到多台服务器。其好处包括：
1. 冗余：如果某台服务器下线，流量会被重新路由。
   - 如果服务器 1 下线，所有流量将被路由到服务器 2。
2. 可扩展性：轻松增加服务器以应对流量高峰。
   - 如果网站流量快速增长，可以增加后续服务器来处理额外流量。

## 第 5 节：数据库复制

<div style="margin-left:3rem">
   <img src="../../01.%20Scaling/images/database-replication.png" width="400" />
</div>

### 主从模型
- **主数据库（Master）：** 处理写操作。
   - 所有修改数据的命令（如 insert、delete 或 update）都必须发送到主数据库。
- **从数据库（Slave）：** 处理读操作，提升性能与可靠性。
   - 由于大多数应用的读远多于写，因此系统中从数据库的数量通常大于主数据库的数量。

### 好处
1. 通过并行读操作提升性能。
2. 通过冗余实现高可用性与数据可靠性。


### 故障处理
- 如果只有一台从数据库可用且它下线了，读操作将临时转向主数据库。
- 如果有多个从数据库可用，读操作会被重定向到其他健康的从数据库，并用一台新服务器替换旧的。
- 如果主数据库下线，一台从数据库将被提升为新的主数据库。
- 在生产系统中，被选中的从数据库可能并不是最新的，因此需要运行数据恢复脚本来更新数据（多主复制、环形复制等方法会有帮助）。

## 第 6 节：缓存
**缓存（cache）**把频繁访问的数据存储在内存中，以减轻数据库负载。缓存层是一个临时的数据存储层，比数据库快得多。

<div style="margin-left:3rem">
   <img src="../../01.%20Scaling/images/cache.png" width="500" />
</div>

### 缓存注意事项
1. **使用场景：** 当数据读多写少的时候，考虑使用缓存。
2. **过期策略：** 缓存数据一旦过期就会被从缓存中移除。如果没有过期策略，缓存数据将永久存储在内存中。
3. **一致性：** 这意味着保持数据存储与缓存同步。由于对数据存储和缓存的修改操作不在同一个事务中，因此可能出现不一致。
4. **缓解故障：** 单台缓存服务器是潜在的单点故障；建议在不同数据中心部署多台缓存服务器，以避免单点故障（SPOF）。
5. **淘汰策略：** 缓存一旦写满，就需要淘汰部分条目以释放内存。LRU（最近最少使用）是最流行的缓存淘汰策略。

## 第 7 节：内容分发网络（CDN）
**内容分发网络（CDN）**通过在地理上分布的服务器上缓存静态内容（图片、CSS、JavaScript）来提升加载速度。

<div style="margin-left:3rem">
   <img src="../../01.%20Scaling/images/cdn.png" width="400" />
</div>

### 工作流程
1. 用户向最近的 CDN 服务器请求内容。
2. 如果未命中，则从源站获取内容并缓存。


### CDN 注意事项
1. **成本：** CDN 由第三方提供商运营，按进出 CDN 的数据传输量收费。
2. **缓存过期：** 缓存过期时间既不宜过长，也不宜过短。
3. **CDN 回退：** 如果 CDN 临时故障，客户端应能检测到问题并转而从源站请求资源。
4. **文件失效：** 如果文件更新了，应使缓存失效，指向更新后的文件。

## 第 8 节：无状态 Web 层
通过将会话数据移到共享数据存储中，Web 服务器变为无状态（stateless）。这带来：
1. 更容易进行水平扩展。
2. 基于流量自动扩缩容。

</div>

## 第 9 节：多数据中心部署
跨多个数据中心部署可提升可用性并降低延迟。策略包括：

<div style="margin-left:3rem">
   <img src="../../01.%20Scaling/images/data-center.png" width="400" />
</div>

1. **GeoDNS 路由：** 将用户引导至最近的数据中心。
2. **数据复制：** 在各数据中心之间同步数据，防止不一致。

### 关键注意事项
- **流量重定向：** 需要有效的工具将流量引导到正确的数据中心。
- **数据同步：** 一种常见策略是在多个数据中心之间复制数据。
- **测试与部署：** 自动化部署工具对于保持所有数据中心的服务一致性至关重要。

---

## 第 10 节：消息队列
**消息队列（message queue）**是一个持久化的组件，存储在内存中，支持异步通信。它充当缓冲区，分发异步请求。

<div style="margin-left:3rem">
   <img src="../../01.%20Scaling/images/message-queue.png" width="500" />
</div>

- 输入服务称为生产者（producer）/发布者（publisher），它们创建消息并发布到消息队列。
- 其他服务称为消费者（consumer）/订阅者（subscriber），它们连接到队列，并执行消息所定义的操作。

## 第 12 节：数据库扩展
### 垂直扩展
- 增加硬件资源，但存在物理与成本上的限制。
- 有多个缺点：
   - 单点故障风险更高。
   - 垂直扩展的总体成本很高

### 水平扩展（分片）

<div style="margin-left:3rem">
   <img src="../../01.%20Scaling/images/horizontal-scaling.png" width="400" />
</div>

- 使用键（例如 `user_id`）将数据划分到多个分片（shard）中。
   - 分片把大型数据库拆分为更小、更易于管理的部分，称为分片。
   - 每个分片共享相同的模式（schema），但每个分片上的实际数据是该分片独有的。
- 实现分片策略时，分片键至关重要。选择分片键时，重要的是选择一个能够均匀分布数据的键。

#### 挑战
1. **数据重分片：** 在以下情况需要重新分片：
   - 单个分片因快速增长而无法再容纳更多数据。
   - 由于数据分布不均，某些分片可能比其他分片更快地耗尽。
   - 一致性哈希（Consistent Hashing）用于解决这些问题。

2. **名人问题（celebrity problem）：** 对某个分片的过度访问可能导致服务器过载。
   - 要解决这个问题，我们可能需要为每个名人单独分配一个分片。

3. **连接与反规范化：** 一旦数据库被分片到多台服务器上，就很难跨数据库分片执行连接（join）操作。
   - 一种常见的变通做法是对数据库进行反规范化，使查询可以在单张表中完成。

---

## 结语
### 关键要点
1. 保持 Web 层无状态。
2. 在每一层都构建冗余。
3. 使用缓存和 CDN 优化性能。
4. 通过分片扩展数据层。
5. 解耦组件以获得灵活性。

本章为构建可扩展、能够承载百万级用户的系统打下了坚实的基础。
