# 第 2 章：粗略估算（Back-of-the-Envelope Estimation）

## 引言
粗略估算（back-of-the-envelope estimation）是系统设计面试中的一项关键技能。它要求进行快速、粗略的计算，以评估系统的容量或性能。正如谷歌高级研究员（Google Senior Fellow）Jeff Dean 所言，这些估算有助于通过思维实验和常见的性能基准，判断设计是否满足需求。

本章将介绍关键概念、方法论和示例，帮助你熟练掌握扩展性与估算能力。

### 程序员都应该知道的延迟数字（Latency Numbers Every Programmer Should Know）
延迟数字表示计算系统中各种操作所花费的时间，这些数字有助于理解操作的相对性能：

| 操作                | 延迟（2020 年） |
|--------------------------|----------------|
| L1 缓存访问          | 0.5 ns         |
| L2 缓存访问          | 7 ns           |
| 主内存访问       | 100 ns         |
| SSD 随机读          | 150 µs         |
| HDD 随机寻道          | 10 ms          |
| 数据中心内往返| 500 µs         |
| 跨区域数据中心往返 | 150 ms         |

**关键结论：**
- 内存很快，磁盘很慢。
- 尽可能避免磁盘寻道。
- 在互联网上传输数据前先压缩，以节省带宽。

---

### 可用性数字
高可用性（high availability, HA）要求停机时间尽可能短。可用性用「几个九」（nines）来表示：
- **99%（两个九）：** 每年停机约 3.65 天
- **99.9%（三个九）：** 每年停机约 8.8 小时
- **99.99%（四个九）：** 每年停机约 52 分钟
- **99.999%（五个九）：** 每年停机约 5.3 分钟
- **99.9999%（六个九）：** 每年停机约 31.56 秒

亚马逊（Amazon）、谷歌（Google）、微软（Microsoft）等云服务提供商的目标都是提供 **99.9% 或更高**的服务等级协议（SLA, Service Level Agreement）。

## 第 2 节：示例估算 —— Twitter 的 QPS 与存储需求

### 假设
- **3 亿月活跃用户（MAU）。**
- **50% 日活跃用户（DAU）。**
- **每个用户每天平均发布 2 条推文。**
- **10% 的推文包含媒体。**
- **数据保留期：5 年。**

### 估算
1. **每秒查询数（QPS）：**
   - DAU = \( 300M x 50\% = 150M \)
   - 推文 QPS = \( 150M x 2 tweets / 24 hour / 3600 seconds = ~3500 )
   - 峰值 QPS = \( 2 x 3500 = ~7000 \)

2. **媒体存储：**
   - **推文大小组成：**
     - `tweet_id`：64 字节
     - `text`：140 字节
     - `media`：1 MB
   - **每日媒体存储量：** \( 150M x 2 x 10\% x 1MB = 30TB per day \)
   - **5 年存储量：** \( 30TB x 365 x 5 = ~55PB \)

## 第 3 节：高效估算的技巧

### 1. 四舍五入与近似
精度并不重要，重要的是过程。用整数来简化复杂计算。例如：
- \( 99987 / 9.1 \) 可以近似为 \( 100,000 / 10 = 10,000 \)。

### 2. 写下假设
清楚记录假设，以便日后参考。

### 3. 标注单位
通过标注单位来避免歧义（例如用 `5 MB` 而不是 `5`）。

### 4. 常见的估算场景
- **QPS（每秒查询数）：** 衡量流量强度。
- **峰值 QPS：** 考虑流量尖峰。
- **存储需求：** 估算总数据量需求。
- **缓存需求：** 评估缓存所需的内存。
- **服务器数量：** 根据工作负载计算硬件需求。
