# 第 11 章：设计信息流系统

## 引言
**信息流系统（news feed system）** 展示一个不断更新的帖子列表（状态更新、照片、视频和链接），这些帖子来自用户的社交关系。典型例子包括 Facebook 的信息流、Instagram 的动态和 Twitter 的时间线。本章探讨如何设计一个可扩展的信息流系统。

---

## 第 1 步：理解问题

### 需求
1. **平台：** 系统同时支持网页和移动应用。
2. **功能：**
   - 用户可以发布帖子。
   - 用户可以在自己的信息流中查看好友发布的帖子。
3. **排序：** 为简单起见，信息流按**逆时间顺序（reverse chronological order）**排序。
4. **规模：**
   - 用户最多可有 5,000 个好友。
   - 1000 万日活跃用户（DAU）。
   - 信息流可能包含文本、图片和视频。

---

## 第 2 步：高层设计

### 概述
该设计包含两条主要流程：
1. **信息流发布（Feed Publishing）：** 用户发布一条帖子，该帖子被写入数据库，并传播到其好友的信息流中。
2. **信息流构建（News Feed Building）：** 用户通过按逆时间顺序聚合好友的帖子来检索自己的信息流。

---

### 信息流 API
1. **信息流发布 API：**
   - **端点（Endpoint）：** `POST /v1/me/feed`
   - **参数：** `content`（帖子文本）和 `auth_token`（认证）。

2. **信息流检索 API：**
   - **端点：** `GET /v1/me/feed`
   - **参数：** `auth_token`（认证）。

1. **用户交互：** 用户通过信息流发布 API 发布一条帖子。
2. **负载均衡器：** 将流量分发到 Web 服务器。
3. **Web 服务器：** 认证请求，并将其转发给相应的服务。
4. **帖子服务（Post Service）：** 将帖子存入数据库和缓存。
5. **扇出服务（Fanout Service）：** 将该帖子传播到缓存中各好友的信息流。
6. **通知服务（Notification Service）：** 向好友发送通知。

2. **负载均衡器：** 将流量分发到 Web 服务器。
3. **Web 服务器：** 将请求转发给信息流服务。
4. **信息流服务（News Feed Service）：** 从信息流缓存中获取帖子 ID，并从数据库或缓存中检索完整的帖子详情。

## 第 3 步：深入设计

### 信息流发布深入剖析
1. **Web 服务器：**
   - 使用 `auth_token` 认证用户。
   - 执行限流以防止垃圾内容。

2. **扇出服务：**
   - **写时扇出（Fanout on Write）：** 在写入时将帖子推送到好友的信息流。
     - **优点：** 实时更新，信息流检索快。
     - **缺点：** 对于好友众多的用户来说资源消耗大。
   - **读时扇出（Fanout on Read）：** 在读取时拉取帖子。
     - **优点：** 对不活跃用户效率高。
     - **缺点：** 信息流检索较慢。
   - **混合方案（Hybrid Approach）：** 对大多数用户采用推送模型（push model），对好友关系众多的用户（例如名人）采用拉取模型（pull model）。

        <img src="../../11.%20News%20Feed%20System/images/feed-publishing-deep-dive.png" alt="信息流发布深入剖析" width="500">

    **扇出服务（fanout service）**的工作方式如下：

    1. **获取好友 ID：** 从图数据库中检索好友列表。
    2. **从缓存中过滤好友：** 访问缓存中的用户设置，以排除某些好友（例如被静音的好友或选择性分享偏好）。
    3. **发送到消息队列：** 将过滤后的好友列表连同新帖子 ID 一起发送到消息队列进行处理。
    4. **扇出工作进程（Fanout Workers）：** 工作进程从消息队列中检索数据，并更新信息流缓存。缓存存储的是 `<post_id, user_id>` 映射，而不是完整的用户和帖子对象，以节省内存。
    5. **存入信息流缓存：** 将新帖子 ID 追加到各好友的信息流缓存中。一个可配置的上限确保只存储最近的帖子，因为大多数用户只关注最新内容，从而使缓存内存消耗保持在可控范围。

## 信息流检索深入剖析

### 缓存架构
缓存分为五层：
1. **信息流缓存（News Feed Cache）：** 存储帖子 ID，以便快速检索。
2. **内容缓存（Content Cache）：** 存储帖子详情（热门帖子放在热缓存中）。
3. **社交图谱缓存（Social Graph Cache）：** 存储用户关系数据。
4. **行为缓存（Action Cache）：** 跟踪用户行为（点赞、回复、分享）。
5. **计数器缓存（Counter Cache）：** 维护点赞、回复、粉丝等的计数。

## 关键优化

### 扩展性
1. **数据库扩展：**
   - 水平扩展和分片（sharding）。
   - 使用读副本（read replica）应对高流量查询。
2. **无状态 Web 层：** 保持 Web 服务器无状态，以支持水平扩展。

### 缓存
1. 将频繁访问的数据存入内存。
2. 使用缓存层来降低延迟和数据库负载。

### 可靠性
1. **一致性哈希（Consistent Hashing）：** 将请求均匀地分布到各服务器。
2. **消息队列：** 解耦系统组件并缓冲流量。

### 监控
1. 跟踪每秒查询数（QPS，queries per second）和延迟等关键指标。
2. 监控缓存命中率，并据此调整配置。
