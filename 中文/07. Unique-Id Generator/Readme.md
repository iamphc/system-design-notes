# 第 7 章：设计分布式唯一 ID 生成器

## 引言
本章讨论为分布式系统设计**唯一 ID 生成器（unique ID generator）**这一挑战。传统的自增主键在分布式环境中并不适用，因为会遇到可扩展性与同步方面的难题。我们的重点是创建唯一、可排序的 64 位数字 ID，并满足以下要求：
- ID 必须**唯一**，并且**按日期排序**。
- ID 必须能容纳在 **64 位**以内。
- 系统每秒应能生成**超过 10,000 个 ID**。

---

## 第 1 步：理解问题
### 基本需求
- ID 必须唯一、是数字，并且能容纳在 64 位以内。
- ID 随时间递增，但并不严格按 `+1` 递增。
- ID 应能按日期排序。
- 系统必须处理高吞吐量（10,000 个 ID/秒）。

---

## 第 2 步：高层设计方案
### 1. 多主复制
- **方案：** 使用数据库的 `auto_increment`，按步长递增（例如 k 台服务器各取 `+k` 的步长）。

    <p align="left">
    <img src="../../07.%20Unique-Id%20Generator/images/multi-master.png"  alt="多主复制" width="400">
    </p>

- **缺点：**
  - 难以跨数据中心扩展。
  - ID 并不总是随时间增大。
  - 增加/移除服务器时存在扩展问题。

### 2. UUID（通用唯一标识符）
- **方案：** 
    - 在每台服务器上独立生成 128 位的唯一标识符，使用 UUID。
    - 各服务器之间无需协调即可独立生成 UUID。

        <p align="left">
        <img src="../../07.%20Unique-Id%20Generator/images/uuid.png"  alt="UUID 生成器" width="600">
        </p>

- **优点：**
  - 服务器之间无需协调。
  - 可随 Web 服务器轻松扩展。
- **缺点：**
  - 超过 64 位的要求。
  - ID 不能按时间排序，而且可能不是数字。


### 3. 票据服务器（Ticket Server）
- **方案：** 使用一台集中式数据库服务器来递增并分配 ID。

    <p align="left">
    <img src="../../07.%20Unique-Id%20Generator/images/ticket-server.png"  alt="票据服务器" width="500">
    </p>

- **优点：**
  - 对小规模系统来说实现简单。
  - 生成数字型 ID。
- **缺点：**
  - 单点故障。
  - 多服务器部署时存在同步难题。

### 4. Twitter Snowflake 方案
- **方案：** 

    <div style="margin-left:3rem">
      <img src="../../07.%20Unique-Id%20Generator/images/twitter-snowflake.png"  alt="Snowflake 方案" width="500">
    </div>
    <div style="margin-left:3rem">
      <img src="../../07.%20Unique-Id%20Generator/images/snowflake-id-breakdown.png"  alt="Snowflake ID 结构分解" width="500">
    </div>

    - 把 ID 划分为若干段，以保证唯一性与可扩展性。
    - **符号位（1 bit）：** 恒为 `0`，可用于区分有符号数与无符号数。
    - **时间戳（41 bits）：** 自自定义纪元（epoch）以来的毫秒数（Twitter 默认值为 `1288834974657`，对应 2010 年 11 月 4 日 01:42:54 UTC）。保证 ID 按时间有序。
    - **数据中心 ID（5 bits）：** 最多标识 `2^5 = 32` 个数据中心。
    - **机器 ID（5 bits）：** 在每个数据中心内最多标识 `2^5 = 32` 台机器。
    - **序列号（12 bits）：** 记录同一毫秒内在某台机器上生成的 ID，每毫秒最多支持 `2^12 = 4096` 个 ID。序列号每毫秒重置为 `0`。



- **优点：**
    - **可扩展性：** 可在多台服务器上处理每秒 10,000+ 个 ID。
    - **时间有序：** 保证 ID 可按时间排序。
    - **去中心化：** 不存在单点故障。


## 第 4 步：其他考量
### 1. 时钟同步
- **挑战：** ID 生成假设各服务器之间时钟是同步的。
- **解决方案：** 使用**网络时间协议（NTP, Network Time Protocol）**来最小化时钟漂移。

### 2. 各段长度调整
- 根据使用场景调整各段大小（例如减少序列号位数、增加时间戳位数）。

### 3. 高可用性
- ID 生成器是关键任务组件，必须具备容错能力。
- 考虑冗余与故障转移（failover）机制。
