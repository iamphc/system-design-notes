# 第 15 章：设计 Google Drive

## 引言
Google Drive 是一项基于云的文件存储与同步服务，允许用户从各种设备存储、访问和共享文件。本章讨论如何设计一个可扩展的系统，它具备以下特性：
- **文件上传与下载**
- **跨设备文件同步**
- **文件共享**
- **文件修订历史**
- **编辑、删除和共享时的通知**

---

## 第 1 步：理解问题

### 关键需求
#### 功能需求：
- 上传和下载文件。
- 在多台设备之间同步文件。
- 维护文件修订版本。
- 支持带权限的文件共享。
- 在文件被编辑、删除和共享时发送通知。

#### 非功能需求：
- **可靠性：** 数据丢失是不可接受的。
- **快速同步速度：** 避免用户因同步延迟而失去耐心。
- **带宽效率：** 尽量减少不必要的数据使用。
- **可扩展性：** 应对 1000 万日活跃用户（DAU）。
- **高可用性：** 在服务器故障或网络问题期间无缝运行。

### 约束与假设
- 用户获得 **10 GB 免费空间**。
- 最大文件大小：**10 GB**。
- 平均文件上传大小：**500 KB**。
- 上传频率：**每用户每天 2 个文件**。
- 所需总存储：**500 PB**。

## 第 2 步：高层设计
### 单服务器设置
一个基础设置包括：
1. **Web 服务器（Web Server）：** 处理上传和下载。
2. **元数据数据库（Metadata Database）：** 跟踪用户数据、登录信息、文件信息等元数据。
3. **存储目录（Storage Directory）：** 存放按命名空间（namespace）组织的文件。


<div style="margin-left:3rem">
    <img src="../../15.%20Google%20Drive/images/namespaces.png" alt="命名空间" width="400" />
</div>

- 设置一台 Web 服务器和一个名为 drive/ 的目录，作为存储已上传文件的根目录。 
- 在 drive/ 目录下，有一系列名为命名空间（namespaces）的目录。 
- 每个命名空间包含该用户上传的所有文件。 
- 每个文件或文件夹都可以通过将命名空间与相对路径拼接起来而被唯一标识。


该设计可作为一个起点，但不足以支撑扩展。

#### API 接口
1. **将文件上传到 Google Drive：** 支持两种上传类型。
    - 简单上传（Simple upload）：在文件较小时使用。
    - 可断点续传上传（Resumable upload）： 
        - 端点：https://api.example.com/files/upload?uploadType=resumable
        - 发送初始请求以获取可续传的 URL。
        - 上传数据并监控上传状态。
        - 如果上传被中断，则断点续传。
2. **从 Google Drive 下载文件：** 下载一个文件时
    -  端点：https://api.example.com/files/download
3. **获取文件修订版本：**
    - 端点：https://api.example.com/files/list_revisions

### 转向分布式系统

#### 改进：
1. **分片（Sharding）：** 基于 `user_id` 将存储拆分到多台服务器。
2. **Amazon S3：** 使用 S3 实现可扩展、冗余的文件存储，并带跨区域复制。

    <img src="../../15.%20Google%20Drive/images/replication.png" alt="复制" width="600" />
     
3. **负载均衡器：** 将流量分发到多台 Web 服务器。
4. **元数据数据库复制：** 通过数据库分片和复制确保可用性。


#### 同步冲突（Sync Conflicts）：
对于像 Google Drive 这样的大型存储系统，同步冲突时有发生。
当两个用户同时修改同一个文件或文件夹时，就会发生冲突。

<div style="margin-left:5rem">
<img src="../../15.%20Google%20Drive/images/sync-conflicts.png" alt="同步冲突" width="600" />
</div>

- 在本例中，用户 1 和用户 2 试图同时更新同一个文件，但用户 1 的文件先被我们的系统处理。
- 用户 1 的更新操作通过了，但用户 2 遇到了同步冲突。 
- 系统呈现同一个文件的两个副本：用户 2 的本地副本和来自服务器的最新版本。
- 用户 2 可以选择合并这两个文件，或者用一个版本覆盖另一个版本。

### 改进后的设计
<div style="margin-left:5rem">
<img src="../../15.%20Google%20Drive/images/high-level-design.png" alt="高层设计" width="500" />
</div>

1. **用户交互：** 用户通过浏览器或移动应用访问该应用。

2. **块服务器（Block Servers）：**
   - 文件被拆分为 **4 MB 的块（block）**（最大尺寸），并被赋予唯一的哈希值。
   - 块独立地存储在云存储中（例如 Amazon S3）。
   - 文件重建涉及按特定顺序把各块拼接起来。

3. **云存储（Cloud Storage）：** 块存储在云存储中，以实现可扩展性和冗余。

4. **冷存储（Cold Storage）：** 不活跃的文件被移到冷存储以降低成本。

5. **负载均衡器：** 将请求均匀地分发到各 API 服务器，以确保高效运行。

6. **API 服务器：**
   - 处理用户认证、资料管理和文件元数据更新。
   - 管理所有非上传类工作流程。

7. **元数据数据库与缓存：**
   - 存储用户、文件、块和版本的元数据。
   - 频繁访问的元数据被缓存，以加快检索。

8. **通知服务（Notification Service）：**
   - 一个**发布/订阅系统（publisher/subscriber system）**，就文件变更（添加、编辑、删除）通知客户端。
   - 确保客户端能够拉取最新更新。

9. **离线备份队列（Offline Backup Queue）：** 临时存储文件变更信息，供离线客户端在重新上线时同步。

### 文件上传流程

1. **文件上传：**
   - 文件被块服务器拆分为块、压缩并加密。
   - 块被上传到块服务器，并存储在 S3 中。
2. **元数据上传：**
   - 客户端向 API 服务器发送元数据。
   - 元数据以 `pending` 状态存入数据库。
3. **完成：**
   - S3 触发一个回调，将文件状态更新为 `uploaded`。
   - 通知服务通知相关用户。

### 文件下载流程
当一个文件在别处被添加或编辑时，会触发下载流程。客户端有两种方式得知这一情况：
- 如果客户端 A 在线，而另一个客户端修改了某个文件，通知服务会通知客户端 A。
- 如果客户端 A 离线，而另一个客户端修改了某个文件，数据会被保存到缓存中。当该离线客户端重新上线时，它会拉取最新的变更。

一旦客户端知道某个文件已被修改，它首先通过 API 服务器请求元数据，然后下载各块以构建该文件。

1. **触发：** 通知服务将文件更新告知客户端。
2. **元数据获取：** 客户端通过 API 检索更新后的元数据。
3. **块下载：** 客户端从块服务器下载更新后的块，并重建文件。

### 通知服务
1. **目的：** 让客户端随时了解文件变更。
2. **机制：** 实现**长轮询（long polling）**以进行异步通知。
3. **示例：** 当一个文件被添加、编辑或删除时，通知会被推送给所有相关客户端。


---

### 存储优化
1. **去重（De-duplication）：** 使用基于哈希的比较，在账户级别移除重复的块。
2. **版本策略：**
   - 限制保存的修订版本数量。
   - 对频繁编辑的文件优先保留近期版本。
3. **冷存储：** 将极少访问的文件移到更廉价的存储方案中（例如 Amazon S3 Glacier）。

---

### 故障处理
1. **负载均衡器故障：** 备用负载均衡器接管并转为活动状态。
2. **块服务器故障：** 待处理任务被重新分配到其他服务器。
3. **元数据数据库故障：**
   - 将一个从节点（slave）提升为主节点（master）。
   - 将流量重定向到剩余的副本。
4. **云存储故障：** 使用跨区域复制来获取不可用的文件。
5. **通知服务故障：** 客户端重连到备用服务器。
