# 第 17 章：附近的人（Nearby Friends）

## 引言

本章聚焦于为一款应用设计可扩展的后端，该应用支持用户分享自己的位置，并发现**附近的**好友。

与邻近服务（proximity service）一章的主要区别在于：在这个问题中，**位置是不断变化的**，而那一章里，商户地址大体上保持不变。

---

## 第 1 步：理解问题并确立设计范围

一些用于引导面试的问题：
 * C：地理上多近才算"附近"？
 * I：5 英里，这个数字应该是可配置的
 * C：距离是按直线距离计算，还是会考虑比如朋友之间隔着一条河？
 * I：是的，这是个合理的假设
 * C：应用有多少用户？
 * I：10 亿用户，其中 10% 使用附近的人功能
 * C：我们需要存储位置历史吗？
 * I：是的，这对比如机器学习很有价值
 * C：我们可以假设不活跃的好友会在 10 分钟后从功能中消失吗？
 * I：可以
 * C：我们需要考虑 GDPR 等合规问题吗？
 * I：不需要，为简化起见

### **功能需求**

 * 用户应该能在移动应用上看到附近的好友。每个好友都带有距离和时间戳，指示该位置是何时更新的
 * 附近好友列表应该每隔几秒更新一次

### **非功能需求**

- **低延迟**：接收位置更新时不应有太大延迟，这一点很重要
- **可靠性**：偶尔丢失数据点是可以接受的，但系统整体应当可用
- **最终一致性**：位置数据存储不需要强一致性。不同副本之间接收位置数据时存在几秒延迟是可以接受的

### **粗略估算**

一些用于确定潜在规模的估算：
 * 附近的好友指 5 英里半径内的好友
 * 位置刷新间隔为 30 秒。人类步行速度很慢，因此不需要过于频繁地更新位置
 * 平均每天有 1 亿用户使用该功能，并发用户占 10%，即 1000 万
 * 平均而言，一个用户有 400 个好友，他们都使用附近的人功能
 * 应用每页显示 20 个附近好友
 * **位置更新 QPS** = 1000 万 / 30 == 每秒约 33.4 万次更新

## 第 2 步：提出高层设计并获得认可

在探讨 API 和数据模型设计之前，我们先研究一下将要使用的通信协议，因为它不像传统的请求-响应通信模型那样无处不在。

### **高层设计**

在高层层面，我们希望在对等节点之间建立有效的消息传递。这可以通过对等网络（peer-to-peer）协议实现，但对于连接不稳定、功耗受限的移动应用来说并不现实。

更实用的方法是使用共享后端，作为向你想要触达的好友进行扇出（fan-out）的机制：

<div style="margin-left:3rem">
    <img src="../../17.%20Nearby%20Friends/images/fan-out-backend.png" alt="扇出后端" width="500" />
</div>

后端做什么？
 * 接收所有活跃用户的位置更新
 * 对于每次位置更新，找出所有应该接收它的活跃用户，并将其转发给他们
 * 如果好友之间的距离超出配置的阈值，则不转发位置数据

这听起来简单，但挑战在于要为我们所处的规模设计系统。

我们先从一个较简单的设计开始，并在深入探讨部分讨论更高级的方案：

<div style="margin-left:3rem">
    <img src="../../17.%20Nearby%20Friends/images/simple-high-level-design.png" alt="简单高层设计" width="500" />
</div>

- **负载均衡器**：将流量分发到 REST API 服务器以及双向 WebSocket 服务器
- **REST API 服务器**：处理辅助任务，如管理好友关系、更新资料等
- **WebSocket 服务器**：有状态服务器，将位置更新请求转发给相应的客户端。它还负责在初始化时向移动客户端播种附近好友的位置（稍后详细讨论）
- **Redis 位置缓存**：用于存储每个活跃用户的最新位置数据。缓存中的每个条目都设置了生存时间（TTL）。当 TTL 到期时，该用户不再活跃，其数据从缓存中移除
- **用户数据库**：存储用户和好友关系数据。可以使用关系型数据库或 NoSQL 数据库
- **位置历史数据库**：存储用户位置数据的历史记录，不一定直接用于附近的人功能，而是用于跟踪历史数据以做分析
- **Redis 发布订阅**：用作轻量级消息总线，为每个用户频道提供不同的主题（topic），用于位置更新

<div style="margin-left:3rem">
    <img src="../../17.%20Nearby%20Friends/images/redis-pubsub-usage.png" alt="Redis 发布订阅的使用" width="500" />
</div>

在上面的示例中，WebSocket 服务器为连接到它们的用户订阅频道，并在收到位置更新时将其转发给合适的用户。

### **周期性位置更新**

周期性位置更新流程的工作方式如下：

<div style="margin-left:3rem">
    <img src="../../17.%20Nearby%20Friends/images/periodic-location-update.png" alt="周期性位置更新" width="500" />
</div>

 * 移动客户端向负载均衡器发送位置更新
 * 负载均衡器将位置更新转发到该客户端对应的 WebSocket 服务器的持久连接上
 * WebSocket 服务器将位置数据保存到位置历史数据库
 * 位置数据在位置缓存中更新。WebSocket 服务器还会在内存中保存该用户的位置数据，用于后续的距离计算
 * WebSocket 服务器通过 Redis 发布订阅在用户的频道中发布位置数据
 * Redis 发布订阅将位置更新广播给该用户频道的所有订阅者，即负责该用户好友的服务器
 * 订阅的 WebSocket 服务器收到位置更新，计算出应该把更新发送给哪些用户，并发送出去

平均而言，由于一个用户平均有 400 个好友，其中 10% 同时在线，因此需要转发 40 次位置更新。

### **API 设计**

我们需要支持的 WebSocket 例程：
 * 周期性位置更新 —— 用户向 WebSocket 服务器发送位置数据
 * 客户端接收位置更新 —— 服务器发送好友的位置数据和时间戳
 * WebSocket 客户端初始化 —— 客户端发送用户位置，服务器返回附近好友的位置数据
 * 订阅新好友 —— WebSocket 服务器发送一个好友 ID，移动客户端应开始跟踪（例如当好友首次上线时）
 * 退订好友 —— WebSocket 服务器发送一个好友 ID，移动客户端应退订（例如好友下线时）

HTTP API —— 用于辅助职责的传统请求/响应负载。

### **数据模型**

 * 位置缓存将存储 `user_id` 与 `lat,long,timestamp` 之间的映射。Redis 是这种缓存的绝佳选择，因为我们只关心当前位置，而且它支持 TTL 淘汰，这正是我们的用例所需。
 * 位置历史表存储相同的数据，但存放在关系表中，包含上述四列。Cassandra 可用于存储这些数据，因为它针对写密集型负载做了优化。

## 第 3 步：深入设计

我们来讨论如何扩展高层设计，使其能够在目标规模下工作。

### **每个组件的扩展能力如何？**

- **API 服务器**：可以通过自动扩缩容组（autoscaling group）和复制服务器实例轻松扩展
- **WebSocket 服务器**：我们可以轻松地水平扩展 ws 服务器，但在拆除服务器时需要确保优雅地关闭现有连接。例如，我们可以在负载均衡器中将一台服务器标记为"排空（draining）"状态，停止向其发送连接，然后再将其从服务器池中移除
- **客户端初始化**：当客户端首次连接到服务器时，它会获取用户的好友列表，在 Redis 发布订阅上订阅他们的频道，从缓存中获取他们的位置，最后转发给客户端
- **用户数据库**：我们可以基于 `user_id` 对数据库进行分片。通过由专门团队管理的专用服务和 API 来暴露用户/好友数据，可能也是合理的做法
- **位置缓存**：我们可以很容易地通过启动多个 Redis 节点来分片缓存。此外，TTL 限制了我们在任一时刻可能占用的最大内存。但我们仍然需要处理大写入负载
- **Redis 发布订阅服务器**：我们利用这样一个事实：如果频道已初始化但未被使用，就不会消耗内存。因此，我们可以为所有使用附近的人功能的用户预分配频道，以避免处理诸如用户上线时新建频道并通知活跃 WebSocket 服务器之类的问题

### **Redis 发布订阅组件的扩展性深入探讨**

我们需要大约 200GB 内存来维护所有发布订阅频道。这可以通过使用两台各 100GB 的 Redis 服务器来实现。

鉴于我们需要每秒推送约 1400 万次位置更新，假设单台服务器每秒可以处理约 10 万次推送，我们至少需要 140 台 Redis 服务器来处理这样的负载。

因此，我们需要一个分布式 Redis 服务器集群来处理高强度的 CPU 负载。

为了支持分布式 Redis 集群，我们需要利用服务发现组件，例如 ZooKeeper 或 etcd，来跟踪哪些服务器存活。

我们需要在服务发现组件中编码的数据如下：

    <img src="../../17.%20Nearby%20Friends/images/channel-distribution-data.png" alt="频道分布数据" width="500" />
</div>

WebSocket 服务器使用从 ZooKeeper 获取的这份编码数据来确定某个频道位于何处。为提高效率，哈希环数据可以缓存在每个 WebSocket 服务器的内存中。

在扩展服务器集群方面，我们可以设置一个每日任务，根据历史流量数据按需扩展集群。我们还可以对集群进行超额配置，以应对负载尖峰。

Redis 集群可以被视为有状态存储服务器，因为频道维护了一些状态，并且需要与订阅者协调，以便他们将工作交接给集群中新配置的节点。

在扩展操作期间，我们必须注意一些潜在问题：
 * 由于频道被移动，WebSocket 服务器会产生大量的重新订阅请求
 * 操作期间客户端可能会错过一些位置更新，这对于本问题是可以接受的，但我们仍应尽量减少这种情况。考虑在当天流量最低点进行此类操作
 * 我们可以利用一致性哈希（consistent hashing），在添加/移除服务器时尽量减少被移动的频道数量

### **添加/移除好友**

每当添加/移除好友时，负责该受影响用户的 WebSocket 服务器需要订阅/退订该好友的频道。

由于"附近的人"功能是一个更大应用的一部分，我们可以假设：无论上述哪个事件发生，都可以在移动客户端侧注册一个回调，客户端会向 WebSocket 服务器发送消息以执行相应操作。

### **好友众多的用户**

我们可以对一个人能拥有的好友总数设上限，例如 Facebook 的好友上限为 5000。

处理这种"鲸鱼"用户的 WebSocket 服务器在其端可能负载更高，但只要我们有足够多的 WebSocket 服务器，应该就没问题。

### **Redis 发布订阅的替代方案**

使用 Redis 做发布订阅的替代方案是利用 Erlang —— 一种通用编程语言，为分布式计算应用而优化。

借助它，我们可以生成数百万个小型的 Erlang 进程，它们相互通信。我们可以在分布式 Erlang 应用中同时处理 WebSocket 连接和发布订阅频道。

不过，使用 Erlang 的一个挑战在于它是一门小众编程语言，可能很难招募到优秀的 Erlang 开发者。

## 第 4 步：总结

我们成功设计了一个支持附近的人功能的系统。

核心组件：
- **WebSocket 服务器**：客户端与服务器之间的实时通信
- **Redis**：位置数据的快速读写 + 发布订阅频道

我们还探讨了如何扩展 RESTful API 服务器、WebSocket 服务器、数据层、Redis 发布订阅服务器，并探讨了 Redis 发布订阅的替代方案。我们还探讨了"附近的陌生人"功能。
