# 第 26 章：支付系统

## 引言
本章将设计一个**支付系统（payment system）**，它支撑着整个现代**电子商务（e-commerce）**。

**支付系统**用于结算金融交易，转移货币价值。

---

## 第 1 步：理解问题并确立设计范围
 * C：我们要构建什么样的支付系统？
 * I：一个面向电商系统的支付后端，类似于 Amazon.com。它处理与资金流转相关的一切事务。
 * C：支持哪些支付方式——信用卡、PayPal、银行卡等？
 * I：现实中的系统应支持所有这些方式。在面试场景下，我们可以只使用信用卡支付。
 * C：我们自己处理信用卡收单吗？
 * I：不，我们使用第三方服务商，如 Stripe、Braintree、Square 等。
 * C：我们在系统中存储信用卡数据吗？
 * I：出于合规原因，我们不直接在系统中存储信用卡数据，而是依赖第三方支付处理商。
 * C：应用是全球性的吗？我们需要支持不同货币和国际支付吗？
 * I：应用是全球性的，但面试中我们假设只使用一种货币。
 * C：每天支持多少笔支付交易？
 * I：每天 100 万笔交易。
 * C：我们需要支持出金流程吗，比如每月向付款方打款？
 * I：是的，我们需要支持。
 * C：还有其他需要注意的吗？
 * I：我们需要支持对账，以修复与内外部系统交互中的任何不一致。

### **功能需求**
 * 入金流程（pay-in flow）——支付系统代表商家从客户那里收款
 * 出金流程（pay-out flow）——支付系统向全球各地的卖家付款

### **非功能需求**
 * 可靠性与容错性。失败的支付需要被谨慎处理
 * 需要在内部系统与外部系统之间建立对账机制

### **粗略估算**
系统每天需要处理 100 万笔交易，即每秒 10 笔交易。

对于任何数据库系统来说，这都不算高吞吐量，因此它不是本次面试的重点。

### **入金流程**
以下是入金流程的高层概览：

<div style="margin-left:3rem">
    <img src="../../26.%20Payment%20System/images/payin-flow-high-level.png" alt="入金流程高层视图" width="500" />
</div>

 * 支付服务（Payment service）——接收支付事件并协调整个支付流程。它通常还会借助第三方服务商做风险检查，排查反洗钱（AML）违规或犯罪活动。
 * 支付执行器（Payment executor）——通过支付服务商（Payment Service Provider, PSP）执行单笔支付订单。一个支付事件可能包含多个支付订单。
 * 支付服务商（PSP）——把资金从一个账户转移到另一个账户，例如从买家的信用卡账户转移到电商网站的银行账户。
 * 卡组织（Card schemes）——处理信用卡操作的机构，例如 Visa、MasterCard 等。
 * 分类账（Ledger）——保存所有支付交易的财务记录。
 * 钱包（Wallet）——保存所有商家的账户余额。

下面是一个入金流程的示例：
 * 用户点击「下单」，一个支付事件被发送到支付服务
 * 支付服务把事件存入自己的数据库
 * 支付服务针对该支付事件包含的所有支付订单调用支付执行器
 * 支付执行器把支付订单存入自己的数据库
 * 支付执行器调用外部 PSP 处理信用卡支付
 * 支付执行器处理完支付后，支付服务更新钱包，记录卖家持有的金额
 * 钱包服务把更新后的余额信息存入数据库
 * 支付服务调用分类账，记录所有资金变动

### **支付服务的 API**
```
POST /v1/payments
{
  "buyer_info": {...},
  "checkout_id": "some_id",
  "credit_card_info": {...},
  "payment_orders": [{...}, {...}, {...}]
}
```

`payment_order` 示例：
```
{
  "seller_account": "SELLER_IBAN",
  "amount": "3.15",
  "currency": "USD",
  "payment_order_id": "globally_unique_payment_id"
}
```

注意事项：
 * `payment_order_id` 会被转发给 PSP 用于支付去重，也就是说，它就是幂等键（idempotency key）。
 * amount 字段使用 `string` 类型，因为 `double` 不适合表示货币金额。

```
GET /v1/payments/{:id}
```

该端点基于 `payment_order_id` 返回单笔支付的执行状态。

### **支付服务数据模型**
我们需要维护两张表——`payment_events` 和 `payment_orders`。

对于支付而言，性能通常不是重要因素，而强一致性才是。

选择数据库时的其他考虑：
 * 有充足的市场供给，可以雇到 DBA 来管理数据库
 * 有良好的记录——该数据库已被其他大型金融机构使用
 * 配套工具丰富
 * 传统 SQL 优于 NoSQL/NewSQL，因为它提供 ACID 保证

`payment_events` 表包含以下内容：
 * `checkout_id`——string，主键
 * `buyer_info`——string（个人备注：用外键关联到另一张表可能更合适）
 * `seller_info`——string（个人备注：同上）
 * `credit_card_info`——取决于卡组织
 * `is_payment_done`——boolean

`payment_orders` 表包含以下内容：
 * `payment_order_id`——string，主键
 * `buyer_account`——string
 * `amount`——string
 * `currency`——string
 * `checkout_id`——string，外键
 * `payment_order_status`——枚举（`NOT_STARTED`、`EXECUTING`、`SUCCESS`、`FAILED`）
 * `ledger_updated`——boolean
 * `wallet_updated`——boolean

注意事项：
 * 一个支付事件会关联多个支付订单
 * 入金流程不需要 `seller_info`，它只在出金时需要
 * `ledger_updated` 和 `wallet_updated` 在调用相应服务记录支付结果时更新
 * 支付状态流转由后台任务管理，该任务检查进行中支付的更新情况，如果一笔支付在合理时间内未被处理，则触发告警

### **复式记账分类账系统**
复式记账机制是任何支付系统的核心。它通过始终把资金操作同时记到两个账户上来追踪资金变动——一个账户余额增加（贷方，credit），另一个减少（借方，debit）：

| 账户 | 借方（Debit） | 贷方（Credit） |
|---------|-------|--------|
| 买家   | $1    |        |
| 卖家  |       | $1     |

所有交易分录之和恒为零。这一机制为系统内所有资金变动提供了端到端的可追溯性。

## 第 3 步：深入设计
本节聚焦于让系统更快、更健壮、更安全。

### **PSP 集成**
如果我们的系统能直连银行或卡组织，就可以不经过 PSP 完成支付。

这类直连非常少见，通常只有那些能证明这笔投资划算的大公司才会这样做。

如果走传统路线，PSP 可以通过以下两种方式之一集成：
 * 通过 API——如果我们的支付系统可以自己采集支付信息
 * 通过托管支付页——以避免处理支付信息相关的监管问题

托管支付页工作流的运行方式如下：

<div style="margin-left:3rem">
    <img src="../../26.%20Payment%20System/images/hosted-payment-page-workflow.png" alt="托管支付页工作流" width="500" />
</div>

 * 用户在浏览器中点击「结账」按钮
 * 客户端携带支付订单信息调用支付服务
 * 支付服务收到支付订单信息后，向 PSP 发送支付注册请求
 * PSP 收到货币、金额、有效期等支付信息，以及一个用于幂等目的的 UUID，通常就是支付订单的 UUID
 * PSP 返回一个 token，唯一标识该支付注册。该 token 存储在支付服务数据库中
 * token 存储好后，用户会被展示一个由 PSP 托管的支付页。该页面使用该 token 以及成功/失败后的跳转 URL 初始化
 * 用户在 PSP 页面填写支付详情，PSP 处理支付并返回支付状态
 * 用户随后被重定向回 redirectURL。跳转 URL 示例——`https://your-company.com/?tokenID=JIOUIQ123NSF&payResult=X324FSa`
 * 同时，PSP 通过 webhook 异步调用我们的支付服务，通知后端支付结果
 * 支付服务根据收到的 webhook 记录支付结果

### **对账**
上一节讲的是支付的正常路径。异常路径则通过后台对账流程来发现和纠正。

每天晚上，PSP 会发送一份结算文件，我们的系统用它把外部系统的状态与内部系统的状态进行比对。

<div style="margin-left:3rem">
    <img src="../../26.%20Payment%20System/images/settlement-report.png" alt="结算报告" width="500" />
</div>

该流程也可以用来检测内部不一致，例如分类账服务与钱包服务之间的不一致。

差异由财务团队人工处理。差异按以下方式处理：
 * 可分类——即已知差异，可以通过标准流程调整
 * 可分类但无法自动化——由财务团队人工调整
 * 不可分类——由财务团队人工调查并调整

### **处理支付处理延迟**
有些情况下，一笔支付可能需要数小时才能完成，尽管它通常只需要几秒钟。

这可能由以下原因导致：
 * 支付被标记为高风险，需要人工审核
 * 信用卡要求额外保护，例如 3D Secure 认证，需要持卡人提供额外信息才能完成

这些情况按以下方式处理：
 * 等待 PSP 在支付完成后向我们发送 webhook；如果 PSP 不提供 webhook，则轮询其 API
 * 向用户展示「处理中」状态，并提供一个可以查看支付进度更新的页面。我们也可以在支付完成后给用户发一封邮件

### **内部服务间通信**
服务之间有两种通信模式——同步和异步。

同步通信（即 HTTP）适合小规模系统，但随着规模增大会暴露出问题：
 * 性能低——调用链涉及的服务越多，请求-响应周期越长
 * 故障隔离差——如果 PSP 或任何其他服务故障，用户将收不到响应
 * 紧耦合——发送方需要知道接收方是谁
 * 难以扩展——没有缓冲，难以应对流量突增

异步通信可以分为两类。

单接收方——多个接收方订阅同一主题，但消息只被处理一次：

<div style="margin-left:3rem">
    <img src="../../26.%20Payment%20System/images/single-receiver.png" alt="单接收方" width="500" />
</div>

多接收方——多个接收方订阅同一主题，消息会被转发给所有接收方：

<div style="margin-left:3rem">
    <img src="../../26.%20Payment%20System/images/multiple-receiver.png" alt="多接收方" width="500" />
</div>

后一种模型很适合我们的支付系统，因为一笔支付可能触发多个由不同服务处理的副作用。

简而言之，同步通信更简单，但不允许服务自治；异步通信则以简单性和一致性换取可扩展性和韧性。

### **处理支付失败**
每个支付系统都必须解决支付失败问题。我们将使用以下机制：
 * 追踪支付状态——每当支付失败时，我们可以根据支付状态决定是重试还是退款
 * 重试队列——需要重试的支付被发布到重试队列
 * 死信队列——彻底失败的支付被推入死信队列，可以在那里调试和检查失败的支付

### **恰好一次投递**
我们需要确保一笔支付只被恰好处理一次，避免向客户重复扣款。

一个操作如果同时满足至少一次（at-least-once）和至多一次（at-most-once），它就是被恰好一次（exactly-once）执行的。

为了实现至少一次保证，我们使用重试机制：

<div style="margin-left:3rem">
    <img src="../../26.%20Payment%20System/images/retry-mechanism.png" alt="重试机制" width="500" />
</div>

以下是决定重试间隔的一些常见策略：
 * 立即重试——客户端在失败后立即发送另一个请求
 * 固定间隔——在重试一笔支付前等待固定时长
 * 递增间隔——逐次增大每次重试之间的间隔
 * 指数退避（exponential back-off）——每次重试间隔翻倍
 * 取消——客户端取消请求。这发生在错误是终局性的或达到重试阈值时

根据经验法则，默认使用指数退避重试策略。一个好的做法是服务器通过 `Retry-After` 响应头指定重试间隔。

重试带来的一个问题是：服务器可能把一笔支付处理两次：
 * 客户端两次点击「支付按钮」，因此被扣款两次
 * 支付被 PSP 成功处理，但下游服务（分类账、钱包）没有处理。重试导致 PSP 再次处理该支付

为了解决重复支付问题，我们需要使用幂等（idempotency）机制——即一个操作无论被执行多少次都只被处理一次的性质。

从 API 角度看，客户端可以发起多次调用，而它们产生相同的结果。幂等通过请求中的一个特殊头（例如 `idempotency-key`）来管理，该头通常是一个 UUID。

<div style="margin-left:3rem">
    <img src="../../26.%20Payment%20System/images/idempotency-example.png" alt="幂等示例" width="500" />
</div>

幂等可以利用数据库添加唯一键约束的机制来实现：
 * 服务器尝试在数据库中插入新行
 * 插入因唯一键约束冲突而失败
 * 服务器检测到该错误，转而把已存在的对象返回给客户端

幂等在 PSP 一侧同样适用，使用前面讨论过的 nonce。PSP 会确保不重复处理带有相同 nonce 的支付。

### **一致性**
在一笔支付的生命周期中，会调用多个有状态服务——PSP、分类账、钱包、支付服务。

任意两个服务之间的通信都可能失败。

我们可以通过实现恰好一次处理和对账来保证所有服务之间的最终数据一致性。

如果使用复制，就必须处理复制延迟，这可能导致用户在主库和副本库之间看到不一致的数据。

为缓解这一问题，我们可以让所有读写都走主库，副本仅用于冗余和故障转移。

或者，我们可以利用 Paxos 或 Raft 这类共识算法，确保副本始终与主库保持同步。我们也可以使用基于共识的分布式数据库，如 YugabyteDB 或 CockroachDB。

### **支付安全**
以下是一些可以用来保障支付安全的机制：
 * 请求/响应窃听——我们可以使用 HTTPS 保护所有通信
 * 数据篡改——强制加密和完整性监控
 * 中间人攻击——使用带证书固定（certificate pinning）的 SSL
 * 数据丢失——跨多个区域复制数据并定期做数据快照
 * DDoS 攻击——实现限流和防火墙
 * 盗卡——使用 token，而不是在系统中存储真实卡信息
 * PCI 合规——针对处理品牌信用卡的组织的安全标准
 * 欺诈——地址验证、卡片验证码（CVV）、用户行为分析等
