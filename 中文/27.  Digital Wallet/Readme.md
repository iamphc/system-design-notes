# 第 27 章：数字钱包

## 引言
**支付平台（payment platform）**通常都有一个**钱包服务（wallet service）**，允许客户在应用内存储资金，之后再提现。

你也可以用它来支付商品和服务，或者把钱转账给其他使用**数字钱包（digital wallet）**服务的用户。相比走普通支付通道，这样做可能更快、更便宜。

## 第 1 步：理解问题并确立设计范围
 * C：我们是否只关注数字钱包之间的转账？还需要支持其他操作吗？
 * I：我们先聚焦数字钱包之间的转账。
 * C：系统需要支持每秒多少笔交易？
 * I：假设 100 万 TPS
 * C：数字钱包有严格的正确性要求。我们可以认为事务保证就足够了吗？
 * I：听起来不错
 * C：我们需要证明正确性吗？
 * I：我们可以通过对账来做到，但对账只能发现差异，而不能告诉我们差异的根因。相反，我们希望能够从头重放数据，以重建历史。
 * C：可用性要求可以定为 99.99% 吗？
 * I：可以
 * C：我们需要考虑外汇吗？
 * I：不需要，它不在范围内

总结一下我们需要支持的内容：
 * 支持两个账户之间的余额转账
 * 支持 100 万 TPS
 * 可靠性为 99.99%
 * 支持事务
 * 支持可复现性

### **粗略估算**
在云上部署的传统关系数据库大约可以支持 1000 TPS。

为了达到 100 万 TPS，我们需要 1000 个数据库节点。但如果每笔转账都涉及转出和转入两侧，那实际上需要支持 200 万 TPS。

我们的设计目标之一是提升单个节点能处理的 TPS，从而减少所需的数据库节点数量。

| 单节点 TPS | 节点数量 |
|--------------|-------------|
| 100          | 20,000      |
| 1,000        | 2,000       |
| 10,000       | 200         |

## 第 2 步：提出高层设计并获得认可

### **API 设计**
面试中我们只需要支持一个端点：
```
POST /v1/wallet/balance_transfer - transfers balance from one wallet to another
```

请求参数——from_account、to_account、amount（用 string 以避免丢失精度）、currency、transaction_id（幂等键）。

响应示例：
```
{
    "status": "success"
    "transaction_id": "01589980-2664-11ec-9621-0242ac130002"
}
```

### **内存分片方案**
我们的钱包应用为每个用户账户维护账户余额。

表示这一数据的一个好结构是 `map<user_id, balance>`，可以用内存版 Redis 存储来实现。

由于单个 Redis 节点扛不住 100 万 TPS，我们需要把 Redis 集群分区到多个节点上。

分区算法示例：
```
String accountID = "A";
Int partitionNumber = 7;
Int myPartition = accountID.hashCode() % partitionNumber;
```

Zookeeper 可以用来存储分区数量和各 Redis 节点的地址，因为它是一个高可用的配置存储。

最后，钱包服务是一个无状态服务，负责执行转账操作。它可以轻松地水平扩展：

</div>

虽然这个方案解决了可扩展性问题，但它不支持原子地执行余额转账。

### **分布式事务**
处理事务的一种方法是在标准的、分片的关系数据库之上使用两阶段提交协议（2PC）：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/distributed-transactions-relational-dbs.png" alt="基于关系数据库的分布式事务" width="500" />
</div>

两阶段提交（two-phase commit, 2PC）协议的工作方式如下：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/2pc-protocol.png" alt="2PC 协议" width="500" />
</div>

 * 协调者（钱包服务）像平常一样在多个数据库上执行读写操作
 * 当应用准备提交事务时，协调者要求所有数据库 prepare（预提交）
 * 如果所有数据库都回复「yes」，协调者再要求各数据库提交事务
 * 否则，要求所有数据库中止事务

2PC 方案的缺点：
 * 因锁竞争而性能不佳
 * 协调者是单点故障

### **使用 Try-Confirm/Cancel（TC/C）的分布式事务**
TC/C 是 2PC 协议的一个变体，它使用补偿事务：
 * 协调者要求所有数据库为事务预留资源
 * 协调者收集各数据库的回复——如果是 yes，要求各数据库 try-confirm；如果是 no，要求各数据库 try-cancel

TC/C 与 2PC 的一个重要区别是：2PC 执行单个事务，而在 TC/C 中有两个独立的事务。

TC/C 分阶段的工作方式如下：

| 阶段 | 操作 | A                   | C                   |
|-------|-----------|---------------------|---------------------|
| 1     | Try       | 余额变动：-$1 | 无操作          |
| 2     | Confirm   | 无操作          | 余额变动：+$1 |
|       | Cancel    | 余额变动：+$1 | 无操作          |

阶段 1——try（尝试）：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/try-phase.png" alt="try 阶段" width="500" />
</div>

 * 协调者在 A 的数据库中开启本地事务，把 A 的余额减少 $1
 * 给 C 的数据库下发一条 NOP 指令，什么也不做

阶段 2a——confirm（确认）：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/confirm-phase.png" alt="confirm 阶段" width="500" />
</div>

 * 如果两个数据库都回复「yes」，进入 confirm 阶段
 * A 的数据库收到 NOP，而 C 的数据库被指示把 C 的余额增加 $1（本地事务）

阶段 2b——cancel（取消）：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/cancel-phase.png" alt="cancel 阶段" width="500" />
</div>

 * 如果阶段 1 中有任何操作失败，进入 cancel 阶段
 * A 的数据库被指示把 A 的余额增加 $1，C 的数据库收到 NOP

下面是 2PC 与 TC/C 的对比：

|      | 第一阶段                                            | 第二阶段：成功              | 第二阶段：失败                        |
|------|--------------------------------------------------------|------------------------------------|-------------------------------------------|
| 2PC  | 事务尚未完成                          | 提交/取消所有事务     | 取消所有事务                   |
| TC/C | 所有事务都已完成——已提交或已取消 | 按需执行新事务 | 回滚已提交的事务 |

TC/C 也被称为基于补偿的分布式事务。高层操作在业务逻辑中处理。

TC/C 的其他特性：
 * 与数据库无关，只要数据库支持事务即可
 * 分布式事务的细节和复杂性需要在业务逻辑中处理

### **TC/C 失败模式**
如果协调者在中途宕机，它需要恢复其中间状态。这可以通过维护阶段状态表来实现，并在各数据库分片内原子更新：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/phase-status-tables.png" alt="阶段状态表" width="500" />
</div>

该表包含的内容：
 * 分布式事务的 ID 和内容
 * try 阶段的状态——未发送、已发送、已收到回复
 * 第二阶段名称——confirm 或 cancel
 * 第二阶段的状态
 * 乱序标志（稍后解释）

使用 TC/C 时的一个注意事项是：在分布式事务进行中，会有一小段时间各账户状态彼此不一致：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/unbalanced-state.png" alt="不平衡状态" width="500" />
</div>

只要我们总能从这种状态中恢复、并且用户不能利用这种中间状态（例如把它花掉），那就没问题。这一点由「始终先执行扣款、再执行入账」来保证。

| Try 阶段的选择  | 账户 A | 账户 C |
|--------------------|-----------|-----------|
| 选择 1           | -$1       | NOP       |
| 选择 2（无效） | NOP       | +$1       |
| 选择 3（无效） | -$1       | +$1       |

注意，上表中的选择 3 是无效的，因为如果不依赖 2PC，我们无法保证跨不同数据库的事务原子执行。

一个需要处理的边缘情况是乱序执行：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/out-of-order-execution.png" alt="乱序执行" width="500" />
</div>

数据库有可能先收到 cancel 操作、后收到 try 操作。这个边缘情况可以通过在阶段状态表中加一个乱序标志来处理。当我们收到 try 操作时，先检查乱序标志是否已设置；如果已设置，则返回失败。

### **使用 Saga 的分布式事务**
另一种流行的方法是使用 Saga——在微服务架构中实现分布式事务的标准。

它的工作方式：
 * 所有操作按一个序列排好。每个操作在自己的数据库内是独立的
 * 操作从头至尾依次执行
 * 当某个操作失败时，整个流程开始用补偿操作回滚，一直回滚到起点

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/saga.png" alt="Saga" width="500" />
</div>

我们如何协调工作流？有两种方法：
 * 编排（Choreography）——参与 Saga 的所有服务订阅相关事件，各自完成 Saga 中自己的部分
 * 协同（Orchestration）——由一个协调者指示所有服务按正确顺序完成各自的工作

使用编排方式的挑战在于：业务逻辑被分散到多个异步通信的服务中。协同方式能很好地处理复杂性，因此它通常是数字钱包系统中的首选方案。

下面是 TC/C 与 Saga 的对比：

|                                           | TC/C            | Saga                     |
|-------------------------------------------|-----------------|--------------------------|
| 补偿动作                       | 在 Cancel 阶段 | 在回滚阶段        |
| 集中协调                      | 有             | 有（协同模式） |
| 操作执行顺序                 | 任意             | 线性                   |
| 并行执行可能性            | 有             | 无（线性执行）    |
| 可能看到部分不一致状态 | 有             | 有                      |
| 应用或数据库逻辑             | 应用     | 应用              |

主要区别在于 TC/C 可以并行化，因此我们的决策基于延迟要求——如果需要低延迟，就应该选 TC/C 方案。

无论采用哪种方案，我们仍然需要支持审计和历史重放，以便从失败状态中恢复。

### **事件溯源**
在现实中，数字钱包应用可能会被审计，我们必须回答某些问题：
 * 我们知道任意给定时刻的账户余额吗？
 * 我们如何知道历史余额和当前余额是正确的？
 * 代码变更后，我们如何证明系统逻辑是正确的？

事件溯源（event sourcing）是一种帮助我们回答这些问题的技术。

它包含四个概念：
 * 命令（command）——来自现实世界的意图动作，例如把 $1 从账户 A 转到 B。由于需要全局顺序，命令被放入 FIFO 队列。
   * 与事件不同，命令可能失败，并带有一定随机性（例如 IO 问题或状态无效）。
   * 命令可以产生零个或多个事件
   * 事件生成可能包含随机性，例如外部 IO。这一点后面会重新讨论
 * 事件（event）——系统中已发生事件的历史事实，例如「已把 $1 从 A 转到 B」。
   * 与命令不同，事件是在我们系统内已经发生的事实
   * 与命令类似，它们也需要排序，因此也被放入 FIFO 队列
 * 状态（state）——某个事件导致的变化结果。例如账户与其余额之间的键值存储。
 * 状态机（state machine）——驱动事件溯源流程。它主要负责校验命令并应用事件来更新系统状态。
   * 状态机应该是确定性的，因此它不应该读取外部 IO 或依赖随机性。

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/event-sourcing.png" alt="事件溯源" width="500" />
</div>

下面是事件溯源的动态视图：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/dynamic-event-sourcing.png" alt="动态事件溯源" width="500" />
</div>

对于我们的钱包服务，命令就是余额转账请求。我们可以把它们放进一个 FIFO 队列，例如 Kafka：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/command-queue.png" alt="命令队列" width="500" />
</div>

完整图景如下：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/wallet-service-state-macghine.png" alt="钱包服务状态机" width="500" />
</div>

 * 状态机从命令队列读取命令
 * 余额状态从数据库读取
 * 校验命令。如果有效，为每个账户生成两个事件
 * 读取下一个事件并应用——更新数据库中的余额（状态）

使用事件溯源的主要优势是它的可复现性。在这个设计中，所有状态更新操作都被保存为不可变的余额变更历史。

历史余额总是可以通过从头重放事件来重建。由于事件列表是不可变的、状态机是确定性的，我们保证能成功重放出任何中间状态。

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/historical-states.png" alt="历史状态" width="500" />
</div>

本节开头提出的所有审计相关问题，都可以依靠事件溯源来回答：
 * 我们知道任意给定时刻的账户余额吗？——可以从头开始重放事件，一直重放到我们关心的时刻
 * 我们如何知道历史余额和当前余额是正确的？——可以从头重新计算所有事件来验证正确性
 * 代码变更后，我们如何证明系统逻辑是正确的？——可以用不同版本的代码跑同一批事件，验证它们的结果完全一致

回答客户关于余额的查询，可以使用 CQRS（命令查询职责分离）架构——可以有多个只读状态机，负责基于不可变的事件列表查询历史状态：

<div style="margin-left:3rem">

## 第 3 步：深入设计
在本节中，我们将探讨一些性能优化，因为我们仍然需要扩展到 100 万 TPS。

### **高性能事件溯源**
我们要探讨的第一个优化是：把命令和事件保存到本地磁盘存储，而不是 Kafka 这类外部存储。

这样既避免了网络延迟，又因为我们只做追加写，这种操作对 HDD 来说通常很快。

下一个优化是在内存中缓存近期的命令和事件，以节省从磁盘重新加载它们的时间。

在底层，我们可以利用 mmap 调用来实现上述优化，它把数据既存到本地磁盘、又缓存在内存中：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/mmap-optimization.png" alt="mmap 优化" width="500" />
</div>

接下来还可以做的优化是：用 SQLite——一个基于文件的本地关系数据库——把状态也存到本地文件系统中。RocksDB 也是一个不错的选择。

就我们的目的而言，我们选择 RocksDB，因为它使用 LSM 树（log-structured merge-tree），针对写操作做了优化。读性能则通过缓存来优化。

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/rocks-db-approach.png" alt="RocksDB 方案" width="500" />
</div>

为了优化可复现性，我们可以定期把快照保存到磁盘，这样就不必每次都从头重建某个状态。我们可以把快照作为大型二进制文件存储在分布式文件存储中，例如 HDFS：

<div style="margin-left:3rem">

### **可靠的高性能事件溯源**
到目前为止做的所有优化都很好，但它们让我们的服务变成了有状态服务。为了可靠性，我们需要引入某种形式的复制。

在此之前，我们应该分析系统中哪些数据需要高可靠性：
 * 状态和快照总是可以通过事件列表重新生成。因此我们只需要保证事件列表的可靠性。
 * 有人可能认为我们总能从命令列表重新生成事件列表，但这不对，因为命令是非确定性的。
 * 结论：我们只需要为事件列表保证高可靠性。

为了实现事件的高可靠性，我们需要把事件列表复制到多个节点上。我们需要保证：
 * 不丢失数据
 * 日志文件内数据的相对顺序在各副本之间保持一致

为实现这一点，我们可以使用共识算法，例如 Raft。

使用 Raft 时，有一个活跃的 leader 和若干被动的 follower。如果 leader 宕机，某个 follower 会接替。只要超过一半的节点存活，系统就能继续运行。

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/raft-replication.png" alt="Raft 复制" width="500" />
</div>

使用这种方案，所有节点都基于事件列表更新状态。Raft 保证 leader 和 follower 拥有相同的事件列表。

### **分布式事件溯源**
到目前为止，我们已经设计出一个单节点性能高且可靠的系统。

我们还必须解决一些局限：
 * 单个 Raft 组的容量有限。到一定阶段，我们需要对数据分片并实现分布式事务
 * 在 CQRS 架构中，请求/响应流程较慢。客户端需要定期轮询系统，才能知道自己的钱包何时更新

轮询不是实时的，因此用户可能要过一段时间才能得知余额更新。另外，如果轮询频率过高，还可能压垮查询服务：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/polling-approach.png" alt="轮询方案" width="500" />
</div>

为缓解系统负载，我们可以引入一个反向代理，由它代表用户发送命令并代用户轮询响应：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/reverse-proxy.png" alt="反向代理" width="500" />
</div>

这样我们可以用单个请求为多个用户拉取数据，从而减轻系统负载，但它仍然没有解决实时接收的问题。

最后一个可以做的改动是：让只读状态机在响应就绪后把响应推回给反向代理。这能让用户感觉更新是实时发生的：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/push-state-machines.png" alt="推送式状态机" width="500" />
</div>

最后，为了让系统进一步扩展，我们可以把系统分片成多个 Raft 组，并在其上用一个协调者（orchestrator）通过 TC/C 或 Saga 实现分布式事务：

<div style="margin-left:3rem">
    <img src="../../27.%20%20Digital%20Wallet/images/sharded-raft-groups.png" alt="分片的 Raft 组" width="500" />
</div>

下面是最终系统中一笔余额转账请求的生命周期示例：
 * 用户 A 向 Saga 协调者发送一个分布式事务，包含两个操作——`A-1` 和 `C+1`
 * Saga 协调者在阶段状态表中创建一条记录，以追踪该事务的状态
 * 协调者确定需要向哪些分区发送命令
 * 分区 1 的 Raft leader 收到 `A-1` 命令，校验它，把它转换成事件，并在 Raft 组内其他节点上复制
 * 事件结果被同步到只读状态机，后者把响应推回给协调者
 * 协调者创建一条记录表明该操作成功，然后继续执行下一个操作——`C+1`
 * 下一个操作的执行方式与第一个类似——确定分区、发送命令、执行、只读状态机推回响应
 * 协调者创建一条记录表明操作 2 也成功，最终把结果告知客户端

---

## 第 4 步：总结
我们设计的演进过程如下：
 * 最初我们用内存版 Redis 的方案。这个方案的问题在于它不是持久存储。
 * 接着我们改用关系数据库，并在其上通过 2PC、TC/C 或分布式 Saga 执行分布式事务。
 * 然后，为了让所有操作都可审计，我们引入了事件溯源。
 * 一开始我们用外部数据库和队列把数据存到外部存储，但那样性能不佳。
 * 于是我们改用本地文件存储，利用追加写操作的性能优势；同时用缓存优化读路径。
 * 上一个方案虽然性能好，但不持久。因此我们引入了带复制的 Raft 共识，以避免单点故障。
 * 我们还引入了带反向代理的 CQRS，代表用户管理事务的生命周期。
 * 最后，我们把数据分片到多个 Raft 组上，并通过分布式事务机制——TC/C 或分布式 Saga——对它们进行编排。
